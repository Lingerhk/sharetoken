# 直连隧道

[English](../tailnet.md) | **简体中文**

买家和卖家都在 NAT 后面时，除非 libp2p 的打洞打通了直连，两端只能经中继相连，而打洞经常不成功。从 1.0.4 起，客户端多了一条通向直连的路：用 Tailscale 的数据面在两台机器之间建一条 WireGuard 隧道。本文说明它是什么、怎么工作、怎么打开和查看状态、实测结果如何，以及它的边界在哪里。设计的简要版本见 [architecture.md](architecture.md) §2.17，安全方面的说明见 [security.md](security.md) §2.9。

## 1. 它是什么

客户端内嵌了 [tailcat](https://github.com/tailscale/tailcat)。这个库把 Tailscale 的数据面单独打包出来，不带控制面：magicsock（找路径和 NAT 穿透）、WireGuard、DERP 中继和用户态网络栈。有了它，共享节点就有一个地址，任何拿到 Ticket 的买家都能拨通，不论两端各在什么网络里。

- 不需要 Tailscale 账号，不装系统 VPN，不需要管理员权限，不用开端口。机器的网卡、路由和 DNS 都不变：隧道终止在客户端进程内部的网络栈里。
- 默认关闭。用 `sharetoken tailnet on` 打开，或者在桌面应用的 设置 → 网络 → “直连隧道” 里打开。买卖两端都要打开。
- 隧道里跑的是一条普通的 libp2p 连接，走 QUIC（默认）或 TCP。连接之上的一切和其他路径上完全一样。
- 中继仍然在用：和协调器之间的流量、卖家的预约，以及隧道没建起来的每一单，都由中继承担。

### 1.1 它用来做什么

没有隧道时，两个都在 NAT 后面的用户之间的一单，除非打洞成功，否则从头到尾走中继：请求和回答（长上下文可达数 MB）都经过中继，受中继的带宽和连接数限制，延迟由中继的位置决定。Tailscale 的穿透比 libp2p 的做得更多：它持续探测，两种地址族和本机每一块网卡都用上，并经 DERP 协调双方同时打洞。在实测的那一对网络上（§8.2），libp2p 四种情况里有三种一直停在中继上，另一种用了约 15 秒；打开隧道后，两个方向都在几秒内直连。

收益有两点：推理流量不再压在中继上，更多的用户之间能建立直连。

### 1.2 它不做什么

- **不保证延迟更低。** 直连路径有多快，取决于两台机器之间的公网路由。离其中一端很近的中继可以一样快：在实测的那一对机器上，小请求的首字节经隧道是 777 ms，经中继是 990 ms（§8.7）。
- **不取代中继和协调器。** 打开隧道的客户端仍然要经中继才能到达协调器，卖家仍然在中继上预约。
- **不增加保护，也不做访问控制。** 身份、保密和计费依靠的仍是原来那些机制（§6）。
- **不隐藏地址。** 直连的两台机器互相看得到对方的 IP 地址。

## 2. 工作原理

```
卖家                                                  买家
libp2p 主机                                           libp2p 主机
 ├ TCP 和 QUIC 传输（原有）                            ├ TCP 和 QUIC 传输（原有）
 └ tailnet 传输                                        └ tailnet 传输
     tailcat 服务端 ─ WireGuard ─ 先经 DERP，再直连 ─────  tailcat 客户端（每个卖家一个）
     隧道内的 4001 端口（UDP 和 TCP）
        └── libp2p 连接：QUIC，或 TCP 加 Noise/TLS 和 yamux ──┘
                 之上：/sharetoken/infer/1.0.2 和其他所有协议
```

代码是一个 libp2p 传输，在 [`internal/tailnet`](../../internal/tailnet)，由 [`internal/client/tailnet.go`](../../internal/client/tailnet.go) 接入客户端。

### 2.1 报价里的地址

打开了隧道的共享节点在离自己最近的 DERP 区域启动一个 tailcat 服务端，在隧道里监听，并在报价里多写一个地址：`/tailcat/<地址>`。这个地址是一个以 `tc` 开头的字符串，里面是服务端的公钥、一个预共享密钥和服务端所在的 DERP 区域。multiaddr 协议 `tailcat` 的编号取自私有区间（`0x30746c`，[`addr.go`](../../internal/tailnet/addr.go)）。

- 这个地址只进报价。它不在 libp2p identify 告诉每个对端的地址里，所以只有协调器派来的买家拿得到。
- 协调器照旧把报价里的地址抄进 Ticket；对它来说这些只是字符串。
- 不认识这个协议名的程序解析不了这个地址，会跳过它。1.0.4 之前的客户端就是这样。隧道关着的 1.0.4 客户端不会拨它。
- 服务端的密钥每次启动都重新生成。卖家重启，或者 `tailnet off` 再 `on` 之后，下一份报价带的是新地址，旧地址不再通向任何地方。

### 2.2 先经 DERP，再直连

DERP 中继是按公钥转发 WireGuard 数据包的 HTTPS 服务器。隧道最初的包经地址里写的那个 DERP 区域转发，所以只要两端都能连上这个区域，隧道就能用。与此同时，magicsock 探测两台机器之间的直连 UDP 路径，找到后把隧道换过去。找不到直连路径时，隧道留在 DERP 上，照常工作。

隧道里跑 TCP 时，对新节点的第一个请求经 DERP 在 1.3 到 1.8 秒内接通，再过 1 到 3 秒隧道换成直连（§8.2）。

买家不采用地址里写的 DERP 主机。它在自己的 DERP 表（`tailnet.derp_map`）里查这个区域，用自己表里的条目；自己表里没有的区域会被拒绝，这一单留在其他路径上。所以卖家无法把买家引到它指定的主机，买卖两端也必须用同一张 DERP 表。两端的默认值都是 tailcat 的公共 DERP 表。

### 2.3 隧道里的 libp2p 连接

隧道承载的是一条 libp2p 连接，连到节点在隧道内 4001 端口上的监听。对端在这条连接的握手里证明身份，和其他连接一样：拨某个节点的隧道地址，应答的却是另一个 peer ID，连接会被断开。以下这些都不变：

- Ticket、收据、确认、计费和争议；
- 推理协议，包括压缩、心跳和续传；
- 三种客户端 API（chat completions、Messages、Responses），它们在买家进程里就终结了，之后才有 libp2p 流；
- 平台的抽检：抽检器只拨卖家在网络中继上的电路地址。

协调器、中继和门户不需要任何改动，也不知道隧道的存在。最初的实测就是对着 1.0.3 的门户、协调器和中继跑的。

### 2.4 拨号顺序与回退

买家对一个还没有连接的节点发起一单时：

1. 拿到 Ticket，里面是节点的各个地址，隧道地址也在其中。
2. 买家另外单独拨一次隧道地址，并要求直连（[`reach.go`](../../internal/tailnet/reach.go) 里的 `Transport.Reach`）。libp2p 的拨号器只要有一个地址接通就停掉其余尝试，而先接通的通常是中继：不另外拨的话，隧道永远建不完。和节点之间已经有直连时（两端在同一个局域网，或者打洞已经成功），不会发起这次拨号。
3. 这一单的流开在最先建好的那条连接上。节点的各个地址里先拨隧道地址；libp2p 本来会把不认识的地址类型排在最后，比其他地址晚一秒。
4. 隧道里的连接建好之后，libp2p 把到这个节点的新流都开在它上面，因为它优先用直连而不是经中继的连接。经中继的那条连接留着自己结束。

所以对一个节点的第一单可能走中继，之后的走隧道。`tailnet.wait_ms` 让一单在第 2 步最多等这么久的直连；续传中的作业从不等待。

节点的报价里列着它监听的所有地址，而拨一个别的网络里的地址只能等到超时。因此客户端对同一个对端最多同时拨 64 个地址，而不是 libp2p 的 8 个，这样那些地址就不会挡住隧道地址和中继地址（[`internal/p2p/host.go`](../../internal/p2p/host.go)）。

以下情况下，这一单和没有隧道时一样走中继：

| 情况 | 结果 |
|---|---|
| 任何一端没开隧道，或者版本低于 1.0.4 | 报价里没有隧道地址，或者地址被跳过 |
| 卖家连不上 DERP 中继 | 报价里没有地址；5 秒后重试，之后间隔逐次加倍，最长 5 分钟，`sharetoken tailnet` 会显示原因 |
| 卖家所在的 DERP 区域不在买家的表里 | 买家拒绝这个地址 |
| 隧道拨号失败或超时（30 秒） | 1 分钟内不再对这个节点尝试 |
| 隧道在一单进行中断开 | 这一单在节点的其他路径上续传（§8.5） |

### 2.5 隧道里跑 QUIC 还是 TCP

共享节点在隧道的同一个端口、同一个地址上两种都提供。买家用 `tailnet.transport` 选择。

| | QUIC（默认） | TCP |
|---|---|---|
| 跑的是什么 | quic-go，每条连接占隧道里的一条 UDP 流，用 libp2p 的 TLS 身份；流就是 QUIC 流 | 隧道的用户态 TCP，再加 libp2p 通常的安全握手和 yamux |
| 数据包 | 最大 1232 字节，即隧道能整包承载的最大数据报；不做路径 MTU 探测 | 隧道的 TCP 分段 |
| 连接何时开始 | 隧道找到直连路径之后，或者在 DERP 上等满 12 秒之后 | 立即开始，经 DERP；换到直连路径时不会变慢 |
| 干净路径上的大请求 | 4 MB 约 0.7 秒 | 4 MB 约 2 秒，和经中继相当 |
| 有丢包或抖动的链路 | 起步阶段出过问题的连接会一直慢（§5） | 比好的 QUIC 连接慢，比坏的稳 |
| 没有直连路径的网络 | 每条新连接都要先等 12 秒 | 不用等 |
| 一个卖家同时的隧道买家数 | 不计入按子网的限额 | 所有隧道地址同在一个 /48 里，受 libp2p 默认的每 /48 64 条连接限制 |

**QUIC 为什么要等直连路径。** quic-go 在往返时间比见过的最小值变长时结束连接的慢启动。两台网络条件都好的机器之间，经 DERP 中继那条路往往更短（实测的那一对是 175 ms 对 200 ms）。在 DERP 上握手的 QUIC 连接随后把直连路径上更长的往返当成拥塞，刚发了十六个包就退出慢启动，之后每个往返只增加一个包：4 MB 要 8 秒，而从直连路径起步的连接是 0.7 秒。所以 QUIC 拨号要等隧道换到直连，从隧道第一次应答算起最多等 12 秒，实在等不到才在 DERP 上开始。等待期间作业走节点的其他路径（[`quic.go`](../../internal/tailnet/quic.go)）。

**握手也允许 12 秒。** 新隧道的第一个 WireGuard 握手包有时会在 DERP 路径刚起来时丢掉，WireGuard 要过五秒才发下一个；quic-go 默认的五秒上限会让这样的握手失败。

**QUIC 不会自动退到 TCP。** 设为 QUIC 的买家在隧道里走不了 QUIC 时，这一单留在节点的其他路径上，一分钟后再试。曾经实现过“记住这个节点只能用 TCP”的回退，后来去掉了：一次偶然的超时就会把买家从此固定在 TCP 上。

修改 `tailnet.transport` 只影响之后拨出的连接。已经建好的连接保持原样，一个客户端可以同时有到不同卖家的 QUIC 隧道和 TCP 隧道。

### 2.6 系统里的 Tailscale 网络

本身运行着 Tailscale 的机器有一个同一 tailnet 的设备都能直接到达的地址（在 `100.64.0.0/10` 或 `fd7a:115c:a1e0::/48` 里），它在 libp2p 不公布的那块网卡上。隧道打开时，共享节点把自己在这个地址上的监听也加进报价，同样在 Tailscale 网络里的买家会在拨隧道地址的同时拨它们。这时路径显示为 `system`。这种模式只有单元测试（§9）。

## 3. 设置和命令

### 3.1 命令行

| 命令 | 含义 |
|---|---|
| `sharetoken tailnet` | 是否打开，本机作为卖家经哪个 DERP 区域可达，每条隧道的路径和传输方式 |
| `sharetoken tailnet on` | 打开 |
| `sharetoken tailnet on -transport tcp` | 打开，并让本机拨出的连接在隧道里跑 TCP（`-transport quic` 换回默认值） |
| `sharetoken tailnet on -wait 3000` | 对一个节点的请求最多等新隧道 3 秒，等不到再走中继（0 到 10000，默认 0） |
| `sharetoken tailnet on -derp-map <URL 或文件>` | 用这张表里的 DERP 中继，代替 tailcat 的公共 DERP |
| `sharetoken tailnet off` | 回到中继和 libp2p 自己的直连 |

`tailnet on` 里没写的参数保持原来的值。设置先保存到 `config.json`，运行中的客户端立即生效，不需要重启。关闭隧道或更换 DERP 表会立刻关掉所有隧道；上面的作业在节点的其他路径上续传。

### 3.2 config.json

| 键 | 默认值 | 含义 |
|---|---|---|
| `tailnet.enabled` | false | 隧道的开关 |
| `tailnet.transport` | `quic` | 本机到卖家的连接在隧道里跑什么：`quic` 或 `tcp`。默认值不写入文件 |
| `tailnet.wait_ms` | 0 | 对一个还没有直连的节点，请求最多等隧道多久（最大 10000）。0：不等 |
| `tailnet.derp_map` | 空 | DERP 表的来源：空为 tailcat 的公共 DERP，或者一个 `http(s)` URL，或者一个文件的路径。取回的表保存在客户端的数据目录里，所以启动时即使连不上提供这张表的服务器，也能找到 DERP |

客户端配置的完整表格在 [configuration.md](configuration.md)。本地 API 提供同样的设置：`GET` 和 `PUT /api/v1/tailnet`（`PUT` 里没写的字段保持原值），`POST /api/v1/tailnet/reload` 重新读取配置文件，隧道打开时 `GET /api/v1/status` 里还有 `tailnet` 一段。

### 3.3 桌面应用

设置 → 网络 里有“直连隧道”开关。勾选后立即生效，并显示同样的三项设置，每项下面有一行说明：传输协议、等待隧道的时间和 DERP 表（界面上叫中转服务器）。“本机”一行说明买家能否经隧道到达这台机器，“当前隧道”面板列出每条隧道的方向、对方、路径、协议、延迟和流量。状态栏用一项显示隧道：未开启；已开启但还没有隧道；或者协议、路径、隧道数量和平均延迟。页面读写的是 `/api/v1/tailnet`；还没接入网络时由守护进程自己保存设置。应用本身的说明见 [desktop.md](desktop.md)。

### 3.4 怎么看 `sharetoken tailnet` 的输出

```
tailnet on (quic), relays from <DERP 表的来源>
   reachable as a seller through DERP region <区域代号>
          PEER  PATH  OVER  ENDPOINT  RTT  CONNS  RX  TX
   to seller    …
   from buyer   …
```

| 部分 | 含义 |
|---|---|
| 第一行 | 开或关；本机拨号用的传输方式；DERP 表的 URL，或 `file`；设置了等待时间时也显示 |
| `reachable as a seller through DERP region …` | 共享已打开，隧道服务端已启动。否则是 `not reachable as a seller: <原因>`，或 `not serving`（共享没开，或服务端正在启动） |
| `this machine is on a Tailscale network …` | 系统里运行着 Tailscale 时显示（§2.6） |
| `to seller` 行 | 本机拨出的隧道。`PEER`：卖家的 peer ID。`CONNS`：隧道上已建立或正在建立的连接数；为 0 的隧道在等待关闭（§4） |
| `from buyer` 行 | 买家连到本节点的隧道，带收到（`RX`）和发出（`TX`）的字节数。这一层不知道买家的 peer ID |
| `PATH` | `direct`；数据包还由 DERP 中继转发时是 `derp:<区域>`；路径未知时是 `tunnel` |
| `OVER` | `quic` 或 `tcp`：隧道上最近一条连接跑的是哪一种 |
| `ENDPOINT`、`RTT` | 直连路径上对方机器的地址，以及最近一次的往返时间 |

隧道打开时，`sharetoken status` 也输出这几行。在用的隧道每 30 秒检查一次路径。

### 3.5 耗时里的 `tailnet=` 字段

每一单的耗时在响应头 `X-Sharetoken-Timing` 里，流式回答则在结尾的注释行里。走了隧道的作业在末尾多一个字段：

```
X-Sharetoken-Timing: ticket_ms=… dial_ms=… upload_ms=… first_byte_ms=… total_ms=… relayed=false … tailnet=direct
```

| 取值 | 含义 |
|---|---|
| 没有 `tailnet=` 字段 | 这一单没有走隧道：`relayed=true` 是经中继，`relayed=false` 是别的直连 |
| `tailnet=direct` | 走隧道，数据包在两台机器之间直接传送 |
| `tailnet=derp:<区域>` | 走隧道，数据包仍由这个 DERP 区域转发 |
| `tailnet=system` | 走系统的 Tailscale 网络（§2.6） |
| `tailnet=tunnel` | 走隧道，但路径当时还不知道 |

路径在作业结束时读取：在 DERP 上开始、在直连路径上结束的作业显示 `direct`，续传过的作业显示它结束时所在的那条连接。`dial_ms` 接近 0 表示连接原来就有。

## 4. 空闲时的行为

| 对象 | 何时关闭 | 时间 |
|---|---|---|
| 买家经隧道到某个卖家的连接 | 上面没有新开的请求 | 10 分钟，每 30 秒检查一次，所以是 10 到 10.5 分钟。进行中的请求会保住它 |
| 隧道本身（一个 WireGuard 引擎，有自己的 UDP 套接字和 DERP 连接） | 上面没有连接 | 再过 2 分钟 |
| 到卖家的隧道 | 已有 16 条，又需要一条 | 关掉最久没有连接的那条。如果每条上都有连接，拨号失败，这一单走中继 |
| 失败的隧道拨号 | | 1 分钟内不再尝试 |
| 卖家一侧 | 共享开着就不关闭 | 客户端重启，或者隧道关了再开，地址会变 |

空闲时间从连接上最后一次开出请求算起，而不是看检查的那一刻碰巧有没有请求：每分钟承载一个短请求的连接算在用。

空闲关闭之后，下一个请求会怎样：

- **在那 2 分钟之内**，隧道还在，直连路径也还在。新连接不需要重新做 WireGuard 握手。
- **超过之后**，买家同时拨隧道和中继，谁先通用谁。两种情况都见过：隧道先通时，这个请求花 0.8 到 2.8 秒拨号，然后直连；中继先通时，这个请求走中继，隧道在后台建立，6 秒后发出的下一个请求已经是直连。

两种情况下请求都不会失败。想让长时间停顿后的第一个请求也走隧道，可以设置 `-wait`；这个设置没有在真机上验证过（§9）。

## 5. 选 QUIC 还是 TCP

QUIC 是默认值，因为在干净的路径上它传大请求明显更快。它有一种隧道内 TCP 没有的失效模式，实测里两面都看到了。

- **干净的有线路径，约 200 ms。** QUIC 上传 4 MB 约 0.7 秒。隧道内 TCP 和中继都是约 2 秒（§8.6）。
- **起步时出过问题的连接会一直慢。** quic-go 的拥塞控制是固定的：Reno 加 HyStart。连接还在起步时，丢一个包，或者某次往返比见过的最小值长出 16 ms 以上，就会退出慢启动；此后窗口每个往返只增加一个 1232 字节的包，在 200 ms 的路径上相当于每发送 1 秒只快约 30 KB/s。请求是一阵一阵发的，中间停顿很久，不发送时窗口不增长，所以这样的连接在它存在期间一直慢；而连接只要每十分钟用一次就不会换。quic-go 没有相关的设置项。
- **不稳定的 Wi-Fi。** 一台用 Wi-Fi 的笔记本，在晚上新建了六条 QUIC 连接，六条都慢：4 MB 要 4 到 34 秒。同一时段同一台笔记本走隧道内 TCP 是 2.4 到 5.6 秒。在更早的一组测试里，同一台笔记本经 QUIC 发 4 MB 只用了 0.77 到 0.92 秒。这只是一台机器，原因也只查到“起步阶段有丢包或延迟抖动”这一步，没有再往下分离。
- **小请求。** 几十 KB 的请求，在中继、TCP 和 QUIC 三条路径上没有可感知的差别。

**建议。** 有线和稳定的链路保持默认值。客户端所在的链路有丢包或抖动，又要发送数 MB 的请求（多张图片、超长上下文）时，用 `sharetoken tailnet on -transport tcp`。这个设置属于买家，因为上传请求的是买家；卖家两种都提供。

## 6. 安全性

正式的说明在 [security.md](security.md) §2.9。概括如下：

- **没有任何保证建立在隧道上。** 隧道里的 libp2p 握手证明对端身份，prompt、Ticket 和收据的保护和其他路径上一样。WireGuard 只是在外面多套了一层加密。
- **隧道地址不是秘密。** 这个节点的每个买家都随 Ticket 拿到它，连同预共享密钥。拿到地址的人只能到达一处：节点在隧道里的 libp2p 监听，也就是它的 TCP 和 QUIC 端口提供的同一个监听。隧道的网络栈上没有别的服务，也不通向这台机器所在的任何网络（没有子网路由，没有出口节点）。
- **DERP 中继看到的和中继一样：** 两端的地址、WireGuard 公钥、交换了多少、什么时候。它看不到内容。区别在于由谁运营：默认的 DERP 中继是 tailcat 的公共 DERP，由 Tailscale 运营，不属于本网络（§9）。
- **卖家不能决定买家连到哪里。** 买家只用自己表里的 DERP 中继（§2.2）。
- **直连的两台机器互相看得到对方的 IP 地址，** 和打洞成功之后一样；打开隧道后这种情况更常发生。只想让中继看到自己地址的用户不要打开隧道，并把 `nat` 设为 false。
- **上限。** 买家最多保留 16 条隧道。卖家最多同时处理 64 个 QUIC 握手，资源管理器的其他限额对隧道连接和对其他连接一样生效。
- **进程里多了代码。** WireGuard、magicsock 和用户态网络栈是一大块依赖。tailcat 固定在一个尚未发布的提交上，并依赖 `tailscale.com` 的预发布版。客户端用不到的功能（SSH、端口映射、强制门户探测等）用构建标签去掉了（[`scripts/build/client-tags.txt`](../../scripts/build/client-tags.txt)），有一个测试保证这份列表和 tailcat 自己的保持一致。
- **关着就是关着。** 隧道关闭时客户端不创建任何引擎，不发任何包；传输虽然装着，但不拨号也不提供服务。

## 7. 兼容性

### 7.1 客户端 API

`/v1/chat/completions`、`/v1/messages` 和 `/v1/responses`，不论流式与否，包括工具调用和 Codex 的 WebSocket，都在买家进程里终结并在那里转换。隧道在 libp2p 连接之下，客户端程序除了 `tailnet=` 字段之外分辨不出它和别的路径。实际跑过的内容见 §8.3 和 §8.4。

### 7.2 上游协议

卖家访问自己的模型服务或托管 API，走的是它自己的出站 HTTPS，隧道不碰这条路：用户态网络栈不改路由，不建网卡，不接管 DNS。厂商的代理设置照常生效；出于同样的原因，隧道也不会妨碍系统 VPN。

### 7.3 网络内的协议

| 机制 | 是否受影响 | 说明 |
|---|---|---|
| 推理协议（压缩、心跳、续传） | 否 | 普通的 libp2p 流；隧道断开的作业在别的路径上续传 |
| 报价、Ticket、收据、确认 | 否 | 协调器仍然只经中继可达；报价里的地址对它只是字符串 |
| 签名域、协议 ID | 否 | 没有变化；不需要升级协议 |
| 平台抽检器发起的抽检 | 否 | 它只拨网络中继上的电路地址 |
| 中继通行证、私有中继、配对 | 否 | 中继上没有任何变化；私有卖家加配对买家的组合实测过（§8.3） |
| 打洞、UPnP | 共存 | 谁先建成直连就用谁；已有直连时不再建隧道 |

### 7.4 新旧版本和不同设置混用

| 买家 | 卖家 | 结果 |
|---|---|---|
| 1.0.4，隧道开 | 1.0.4，隧道开 | 隧道 |
| 1.0.4，隧道开 | 1.0.4 隧道关，或更早的版本 | 报价里没有隧道地址：中继或 libp2p 自己的直连 |
| 1.0.4 隧道关，或更早的版本 | 1.0.4，隧道开 | 地址被跳过：中继或 libp2p 自己的直连。1.0.3 买家的日志里没有解析报错 |
| 1.0.4，QUIC | 隧道里只提供 TCP 的 1.0.4 预发布构建 | 中继：QUIC 握手 12 秒后超时，买家记一条日志，一分钟后再试。同一个买家改用 `-transport tcp` 就能走隧道 |
| 任意 | 1.0.3 的协调器、中继和门户 | 可用；隧道不需要它们做任何事 |

### 7.5 同一个地址后面有很多客户端

这一项和隧道无关，是测试隧道时发现的：中继和协调器原来对同一个公网 IPv4 地址只接受 8 条连接，这是 libp2p 的默认值，所以同一个办公室或家庭地址后面的第九个客户端会被每个中继拒绝。从 1.0.4 起，中继和协调器对每个 IPv4 地址、每个 IPv6 /56 接受 32 条连接，对每个 IPv6 /48 接受 256 条，是 libp2p 默认值的四倍（[`internal/p2p/host.go`](../../internal/p2p/host.go)）。同一个地址后面大约 32 个客户端可以共用一个中继。这一项需要中继和协调器升级到 1.0.4。

实测中还看到：连不上卖家任何一个中继的买家，只要拿得到 Ticket，单靠隧道地址也能连上卖家。

### 7.6 平台

六个目标（macOS、Linux、Windows 各自的 amd64 和 arm64）都能用 `CGO_ENABLED=0` 构建。Linux 上不需要 `/dev/net/tun`，也不需要 `CAP_NET_ADMIN`；§8.1 的云虚拟机上客户端以普通用户运行。在真机上验证过、买家和卖家两种角色都跑过的有：macOS（arm64）、Linux（amd64）和 Windows 11（§8.3）。

## 8. 实测结果

### 8.1 测试环境

- 一台在家庭 NAT 后面的笔记本（macOS，arm64），用 Wi-Fi。第一组隧道测试里它的 `nat` 设置是关的（没有端口映射，不打洞），用来模拟 libp2p 建不成直连的网络。
- 一台在 NAT 后面的云虚拟机（Linux，amd64），以普通用户运行。两者之间约 200 ms。
- 一台 x86 Linux 虚拟机（Ubuntu 24.04）和一台 Windows 11 虚拟机，在同一条家庭宽带后面的有线局域网里。
- tailcat 的公共 DERP 中继。
- 卖家提供五个用 API key 的模型（DeepSeek、两个 Anthropic 模型、一个 OpenAI 模型、一个 Gemini 模型），另有一个私有卖家提供 ChatGPT 订阅的两个模型。它们的上游接口分别是 chat completions、Messages 和 Responses。

这只是一对网络。它没有覆盖到的情况列在 §9。

### 8.2 接通

| 情况 | 结果 |
|---|---|
| 不开隧道，`nat` 开（家里的路由器做端口映射），云虚拟机向笔记本买 | 一直经中继（30 秒内没有升级）；首次拨号 5.9 秒 |
| 不开隧道，`nat` 开，笔记本向云虚拟机买 | 约 15 秒后打洞成功 |
| 不开隧道，笔记本的 `nat` 关，两个方向 | 一直经中继 |
| 开隧道（隧道内 TCP），对新节点的第一个请求 | 拨号 1.3–1.8 秒，路径 `derp:<区域>` |
| 同一条隧道，1–3 秒之后 | `direct`，往返 204–216 ms |
| 之后的请求 | 拨号约为 0，全部 `relayed=false tailnet=direct` |
| 开隧道（隧道内 QUIC），第一个请求，Linux 虚拟机 / Windows 虚拟机作买家 | 拨号 1.8 秒 / 2.2 秒，直连 |
| 开隧道（隧道内 QUIC），云虚拟机发来的第一个请求，Linux 虚拟机 / Windows 虚拟机作卖家 | 拨号 0.9–1.3 秒 / 0.9–1.4 秒，直连 |
| 两端在同一个局域网 | 不建隧道：本来就是直连 |

### 8.3 协议矩阵

每个模型跑 51 个用例：12 个场景（基本对话、系统提示加多轮、工具循环、截断、推理、不推理、JSON schema、图片、错误请求、未知模型、长 prompt、并发突发），覆盖三种客户端 API，流式和非流式。

| 隧道内 | 买家 → 卖家 | 模型 | 通过 |
|---|---|---|---|
| TCP | 笔记本 → 云虚拟机 | 5 个用 API key 的 | 254 / 255 |
| TCP | 云虚拟机 → 笔记本 | 5 个用 API key 的 | 254 / 255 |
| TCP | 云虚拟机 → 笔记本，私有卖家加配对买家 | ChatGPT 订阅的 2 个 | 102 / 102 |
| QUIC | 笔记本 → 云虚拟机 | 5 个用 API key 的 | 254 / 255 |
| QUIC | 云虚拟机 → 笔记本 | 5 个用 API key 的 | 255 / 255 |
| QUIC | Linux 虚拟机作买家 | 3 个 | 153 / 153 |
| QUIC | Windows 虚拟机作买家 | 3 个 | 151 / 153 |
| QUIC | Linux 虚拟机和 Windows 虚拟机作卖家，合计 | | 102 / 102 |

所有失败都是同一个用例：DeepSeek、图片、非流式。给它一张纯红色的图片问是什么颜色，模型回答 “White”。请求和响应本身是完整的；事后在隧道上把图片场景重跑三轮，9 个全部通过。

TCP 的几行里，每个请求走的路径都从买家日志里逐条统计过：300 个里 300 个直连；304 个直连加 1 个在 DERP 上；137 个里 137 个直连。没有一个经中继。这几轮里两端都没有记录错误，也没有一次收据确认失败。

### 8.5 隧道出问题时

| 情况 | 隧道内 TCP | 隧道内 QUIC |

云虚拟机作买家，卖家在有线局域网里（中继和 TCP 各 4 次；QUIC 每个大小 8 次，四条新建的连接各两次）：

| 1 MB | 1.09–1.29 s | 1.40–1.48 s | 0.28–0.93 s |
| 4 MB | 1.5–2.2 s | 1.8–2.3 s | 0.66–0.72 s（四条连接里有一条：1.56 s） |
| 8 MB | 2.6–3.0 s | 2.6–2.8 s（另有两次：10 s） | 0.85–1.0 s（四条连接里有一条：4.0–4.3 s） |

笔记本作买家，云虚拟机作卖家（三轮里的两轮；第三轮两种都慢，4 MB 要 7.6–11.8 s）。这个方向没有中继的数值：测试期间这个买家连不上卖家的中继（§7.5）。

| 请求体 | 隧道，TCP | 隧道，QUIC |
|---|---|---|
| 256 KB | 0.84–0.86 s | 0.22–0.67 s |
| 1 MB | 1.51–1.55 s | 0.29–0.45 s |
| 4 MB | 2.7–3.1 s | 0.77–0.92 s |
| 8 MB | 4.2–6.0 s | 1.1–1.5 s |

新建 QUIC 连接，每条连接上发两次 4 MB，是后来晚上的一组测试：

| 买家 | 连接数 | 快的 | 慢的 |
|---|---|---|---|
| Linux 虚拟机，有线 | 8 | 7 条：第一次 1.39–1.48 s（含起步），第二次 0.66–0.76 s | 1 条：5.3 s 和 4.4 s |
| 笔记本，Wi-Fi | 6 | 0 条 | 6 条：最好的一条 4.1 s 和 4.1 s，其余 12.8–33.7 s |

同一个半小时里，笔记本走隧道内 TCP（新建两条连接）1 MB 用 1.3–1.9 s（有一次 9.7 s），4 MB 用 2.4–5.6 s；有线的 Linux 虚拟机作买家发 4 MB，经中继 1.71–2.20 s，经 TCP 2.04–2.47 s，经 QUIC 0.65–0.73 s。

慢的连接不会自己好起来。有一条在别的请求进行中建起来的连接，连着发了八个大请求体，速率依次是 0.33、0.55、0.75、0.96、1.1、1.2、1.3、1.4 MB/s：一条直线，每发送 1 秒快约 30 KB/s（§5）。

隧道内跑 TCP 时，更早在同一对网络上做的一组测试发现：几百 KB 以内的请求体和经中继差不多快，1 MB 及以上的从持平到慢数倍不等，随方向和时段变化（16 MB：9–15 s，经中继是 4.5 s）。tailcat 自带的测速在同一条隧道上测得 TCP 40–60 Mbit/s。原因判断为隧道的用户态 TCP 独自在整条 200 ms 的路径上做拥塞控制，而中继把这条路拆成了两段较短的、各由内核 TCP 负责的路径；这个判断没有抓包证实。加入 QUIC 正是因为这个发现。

## 9. 边界和未决事项

- **公共 DERP 中继是别人提供的免费服务。** tailcat 的公共 DERP 由 Tailscale 运营，有限速，没有服务保证，条款也可能变化。测试里它们承载了 MB 级的上传（§8.5）；更大的流量没有试过。从中国大陆的一台服务器上测，公共 DERP 表和其中四个区域都能连上，但 TLS 握手要 2 到 7 秒：能用，但不可依赖。网络在把隧道设为默认开启之前，应当运行自己的 DERP 中继，并把这张表发给买卖两端。
- **QUIC 的拥塞控制无法调整。** quic-go 用的是 Reno 加 HyStart，没有更换的选项。过早退出慢启动的连接在长路径上会一直慢（§5）。在这一点改变之前，链路不好的客户端的办法就是 `-transport tcp`。
- **没有直连路径的网络里，每条新的 QUIC 连接要等 12 秒。** 隧道只能留在 DERP 上时，每条新的 QUIC 连接都要等满 12 秒才在 DERP 上开始；这期间请求走中继。隧道内 TCP 没有这个等待。
- **长时间停顿后的第一个请求经常走中继。** 这是设计如此：除非设置了 `tailnet.wait_ms`，请求不等隧道。
- **卖家一直留在启动时选定的 DERP 区域。** 这个区域故障期间，新买家建不了隧道，走中继；已经直连的隧道不受影响。
- **没有在真机上验证过的：** 系统的 Tailscale 网络（§2.6，只有单元测试），以及 `tailnet.wait_ms`。
- **只有一对网络。** 一边是家庭 NAT，一边是云上 NAT，相距约 200 ms，同一个卖家上最多同时有三个买家。对称 NAT 和运营商级 NAT、总体的直连成功率、大量买家同时连接、DERP 上的大流量，都没有数据。
- **依赖还没有发布稳定版。** tailcat 的 API 可能还会变；升级之后需要把 §8 的测试重跑一遍。
