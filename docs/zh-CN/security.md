# 安全性

[English](../security.md) | **简体中文**

ShareToken 让人们向自己控制不了的机器购买推理，用平台保管的 credit 付款，并通过第三方运行的中继互相连接。本文说明谁在什么事情上受信任，每一方能做什么、不能做什么，以及保护到哪里为止。背后的设计见 [architecture.md](architecture.md)。

## 1. 各方及其受信任的范围

| 一方 | 在什么上受信任 | 在什么上不受信任 |
|---|---|---|
| 买家的客户端 | 自己的 prompt 和 credit | 诚实付款：它可能拒签一张有效的收据 |
| 卖家的客户端 | 它所处理作业的明文（运行在 TEE 里时除外） | 运行声称的模型、如实报告用量、原样返回模型的输出 |
| 中继 | 转发字节 | 其他任何事。它能看到谁和谁通信、流量多少，看不到内容 |
| 私有中继（用户自己运行，§2.8） | 向它主人的节点转发字节 | 其他任何事，而且比网络的中继看到的更少：和协调器之间的流量不经过它 |
| 协调器 | 账本、撮合、争议裁决 | prompt 和答案：它们不经过协调器。只有买家把某一单作为证据披露时，协调器才看到这一单的内容 |
| 门户 | 账户（邮箱，没有密码）、登录验证码（加盐哈希）、token（哈希）、两步验证密钥（加密）、设备绑定、credit 发放 | prompt 和答案、设备私钥 |
| 网络 | 无 | |

每一方都是一个 libp2p Ed25519 身份。报价由卖家签名，Ticket 由协调器签名，收据由卖家签名，确认由买家签名。每个签名覆盖的是带长度前缀的规范编码，并带有各自的域字符串（`internal/canon`、`internal/protocol`），所以为一种消息做的签名不能被当作另一种消息重放。

## 2. 买家可以依赖什么

### 2.1 传输途中的保密

prompt 只从买家到卖家，不去别处。它有两层保护：

- **传输层。** 每条 libp2p 连接都用 Noise，在两个对端之间端到端加密，经中继承载时也一样。中继转发的是密文。
- **封装加密**（`internal/box`）。买家用这一单新生成的 X25519 密钥把请求封装给卖家的 box 公钥：X25519 ECDH、HKDF-SHA256、AES-256-GCM。卖家把响应作为一条带编号的流来封装，用的是双方从同一次密钥协商推出的一把密钥，这把密钥绑定了作业、方向和双方的公钥，帧的序号就是 nonce。附加数据把每段密文绑定到它的作业，把每个响应帧绑定到它的序号，所以密文不能被挪到另一单，也不能被重排。

  买家也能推出这把响应密钥，因而能造出可以解开的帧。这对它没有用：卖家交付了什么由收据确定，收据签的是密文本身的哈希（2.2）；在改用流密钥之前，任何人也都能同样地把一个分块封装给买家的公钥。

- **长度和时间**（`protocol/codec.go`）。请求在封装前先压缩，再补齐到分档长度（每档增加四分之一），中继只能看出它的大小在哪个 25% 区间。响应是一条压缩流，卖家最多每 50 毫秒切出一帧，同时到达的 token 共用一帧，每帧补齐到 32 字节的整数倍（超过 1 KiB 时按 256 字节）。所以中继无法从帧长读出单个 token 的长度，公开的针对流式回答的攻击正是靠这个。只做压缩反而会更糟（压缩后的大小反映文本的重复程度），所以压缩和填充一起做。仍然可见的有：帧的发送时间，也就是 50 毫秒粒度的回答节奏，以及回答的总大小。

之所以还要第二层，是因为有两件事第一层做不到：box 密钥可以放在 TEE 里，而终止 Noise 的是宿主机的网络栈；收据是对封装后的字节计算的。

控制面（Ticket、收据、争议）经中继时同样是 Noise 端到端，所以中继也看不到这些。

### 2.2 答案的完整性

卖家签发一张收据（`internal/receipt`），内容是：对于封装后字节哈希为某个值的请求，我返回了封装后各帧哈希为某个值的响应，用的是这个模型，消耗了这么多 token。买家的客户端用自己实际收发的字节重新计算这两个哈希，并在每一帧到达时校验它的认证标签和顺序。卖家不能签一份记录而交付另一份，中间任何人改动、丢弃或重排帧都会让校验失败。

非流式响应在收据验证通过之后才返回给调用方（`X-Sharetoken-Verified: true`）。流式响应边到边转发，结尾附一行注释说明验证结果。

### 2.3 计费真实

收据里还有 token 数，买家的客户端会根据收发的内容估算它。数字不合理时，客户端拒签并带着证据发起争议（`internal/evidence`）。证据包括这一单的私钥、封装后的请求和封装后的响应帧。请求是用这一单专用的密钥封装的，卖家用从这把密钥推出的密钥封装每一帧，所以协调器不需要信任买家就能核验：

- 请求和各帧正是卖家签过名的那些；
- 披露的密钥就是请求当初承诺的那一把；
- 每一帧能否用推出的密钥解开并解码；
- 全文实际有多少 token。协调器有该模型的参考副本时，用参考分词器来数（`internal/tokens`）。

被披露的只有这一单，因为每一单的密钥都不同。协调器只在裁决期间把明文留在内存里，记录下来的只有结果。如果买家主张的是卖家从未签过名的字节，这种方式无法判定，要交给管理员处理。

### 2.4 模型就是声称的那个

收据证明的是返回了什么，证明不了是哪个模型生成的。有两种机制处理这个问题：

- **抽检**（`internal/audit`）。协调器在随机时刻走普通买家的路径，向卖家买几个回答（默认 5 个），三种接口都会用到，题目是开放题（解释、建议、改写；答案唯一的题看不出是哪个模型），用贪心解码。然后由协调器自己的参考模型逐 token 读卖家的回答：逐 token 强制核对（teacher forcing）在每个位置给出卖家的 token 是不是参考模型自己的首选（自建 vLLM 每个回答一次调用，DeepSeek 的前缀续写每个 token 一次调用）；参考方只对自己生成的内容给 logprobs 时（OpenAI），卖家的回答如果偏离参考模型的贪心回答，偏离处必须是近乎平局的选择。按全部题目的均值判定，阈值按参考模型分别校准：参考模型每天给自己的回答打分，这就是诚实卖家会得到的分数。计费按参考模型的 token 数核对。明显不符会扣信誉，连续不符会让卖家被暂停接单；介于两者之间的算无结论，不扣分。新的参考模型先以影子模式运行（只记录结论），诚实分数发生漂移的（服务商换了同名模型）也一样。参考方不给 logprobs 的模型（Claude、Gemini）只核对计费。题目由用户的客户端转交给卖家（`internal/coordinator/errand.go`）：客户端不定期问协调器有没有要转交的题，拿到后当作自己的作业去跑，用的是自己的设备身份和平时买东西的那条连接，所以卖家看到的是一个它可能本来就认识的买家。有多个客户端可用时，一次抽检的每道题由不同的客户端转交。请求由协调器用自己留着的密钥加密：客户端看不到题目和回答，也改不了，因为卖家的收据签了两者的哈希，协调器会按收据核对带回来的内容。票据由平台付费，不花客户端的钱。只有本来就可能被撮合到这个卖家并付费的客户端才会转交：卖家自己的设备、它的共享伙伴、私有卖家的陌生人都不会。用户可以关掉转交，只能在客户端的配置文件里关（`buy.spot_checks`）。没有客户端可以转交时，抽检用自己的新身份去问，这时只经协调器自己的中继电路连接卖家：从不直连（那会让卖家看到协调器的地址），也不经任何其他中继（`audit.delivery`）。
- **硬件证明**（`internal/attest`）。运行在 AMD SEV-SNP 或 Intel TDX 机密虚拟机里的卖家公布一份由 CPU 签名的 quote，覆盖虚拟机的启动度量值和它两把密钥的哈希。买家验证 quote 并在自己的白名单里找到这个度量值之后，就知道 prompt 只会在这个镜像内部被解密，收据也是这个镜像签的。两把密钥都被绑定：如果只绑定签名密钥，宿主机就可以把 box 密钥留在虚拟机外面。

### 2.5 卖家一侧

- **卖家干了活就能拿到钱。** 签发 Ticket 时买家的 credit 已被冻结。买家要拒签有效的收据就必须发起争议，而证据会证明收据是对的。
- **Ticket 不能被重放，也不能被别人拿去用。** 它写明了买家、卖家、作业和过期时间，卖家对每一单只服务一次。
- **买家拿了 Ticket 却不来连接**，占用卖家名额的时间是有上限的：未开始的作业在 Ticket 过期后不久被释放，冻结额退回，卖家的信誉不受影响；一个账户持有的闲置 Ticket 达到上限后，就拿不到新的。
- **卖家在交付任何内容之前失败**时会放弃这一单，买家的冻结额立即退回。
- **用户不能和自己交易**来刷信誉：撮合会排除买家账户名下的所有设备。

### 2.6 自己选定卖家

不希望 prompt 发给任意卖家的买家，可以和自己认识的卖家配对（`internal/accounts/pairing.go`）。卖家发出配对码，买家兑换，此后协调器只把这个买家的请求撮合给和它配对的卖家，也只列出他们的模型。这条规则由协调器在每次请求时执行，对账户名下的所有设备生效，请求指定了节点也一样，所以改过的客户端绕不过去。

- 配对码是 80 位随机数，会过期（默认一天，最长 30 天），可以限定买家数，也可以撤销。输错配对码按账户和地址限流，和登录失败一样。
- 双方看到的对方账户名是打码的。配对码泄露后，陌生人可以和卖家配对。对开放的卖家，他得到的不比一个没有配对的买家多；对私有卖家，他就能购买了。卖家能看到每一个配对并移除它，也可以给配对码限定买家数。
- 配对约束的是买家。卖家照常服务没有和它配对的买家，除非开启私有模式：这时协调器只把和它配对的买家撮合给它，并对其他人隐藏它的模型。
- 一个买家最多和三个卖家配对。
- 私有卖家和其他卖家一样接受抽检：由它已配对买家的客户端转交题目；没有这样的客户端时，协调器的抽检身份可以被撮合到它。买家很少的私有卖家能猜出陌生的对端是抽检，所以对这类卖家，不经转交的抽检能证明的更少。
- 管理员能看到所有配对，以及双方完整的账户名。

### 2.7 共享伙伴

两个用户可以结成共享伙伴，免费使用对方的节点（`internal/accounts/sharing.go`）。和配对一样，这是协调器在每次请求时执行的撮合和计费规则：它先试伙伴的节点，并把这样的 Ticket 标为 `Shared`，这是签名字段，双方都改不了，所以这个任务不动 credit。任务的其他方面都不变：伙伴的节点和任何卖家一样能看到 prompt，回执、哈希和抽检照常进行。

- 邀请码和配对码一样是秘密：80 位随机数，默认有效一天、最长 7 天，只能让一个人加入，可以撤回。输错邀请码按账户和地址限流，和登录失败一样。邀请码泄露后，陌生人可以在额度内免费使用邀请者的节点；邀请者能看到这个伙伴，也可以解除。
- 双方看到的对方账户名是打码的，还能看到最近 24 小时双方互相用了多少 token。管理员能看到所有共享组和完整的账户名。
- 用户给出的量由它自己的设置限定：滚动 24 小时的 token 数（按已结算的任务计，所以运行中的任务会让它略微超出）和每个节点并发槽位的比例（0 表示暂停）。一个用户最多 5 个伙伴。
- 不论用户有没有配对，伙伴都会参与撮合；私有卖家照样为伙伴服务：私有模式只针对付费买家。

### 2.8 私有中继

用户可以运行自己的中继（`relay init`，和网络的中继是同一个程序），让别人经它访问自己共享的节点（客户端配置里的 `private_relays`）。三条规则保证这样的中继知道的、能决定的都不比卖家本来就有的更多：

- **只接纳主人。** 中继列出账号（`access.networks[].allow_accounts`）。门户把账号签进每一张中继凭证，所以中继离线就能判断是否接纳这些账号的设备；新设备不需要改中继，被禁用的用户的凭证在有效期内失效。它上面没有协调器（没有 `allow_peers`）。
- **和协调器之间的流量从不经过它。** 客户端把私有中继放在单独的列表里，选择通往协调器的路径时从不读取这个列表（`internal/client/private_relays.go`）；协调器只在门户登记的中继上预约。所以运行私有中继的人看不到协调器的地址，也看不到哪些用户在线：只看到在它上面预约的节点，以及连到这些节点的买家。
- **平台自己的抽检连接从不经过它。** 抽检身份只拨已登记中继的 circuit（§2.4）。私有中继后面的节点照样被抽检，由买家客户端转交的作业完成：转交方按节点给出的地址拨号，和发自己的请求一样。

私有中继不需要登记：门户和协调器不知道它存在，只在节点的报价里看到它的 circuit 地址。只要有一个私有中继上的预约有效，节点就不在网络的中继上预约（除非设置了 `share.keep_official`）；半分钟内一个都没有时，退回网络的中继。

### 2.9 直连隧道

`sharetoken tailnet on` 之后，都打开了它的买家和卖家之间可以用一条 WireGuard 隧道（Tailscale 的数据面，即 tailcat 库）代替中继（[architecture.md](architecture.md) §2.17）。

- **安全不依赖隧道。** 隧道里跑的是和别处一样的 libp2p 连接（QUIC 或 TCP）：对端在握手里证明身份，prompt、Ticket 和收据的保护照旧。隧道的密钥写在节点的报价里，节点的每个买家都拿得到：它不用来把谁挡在外面。拿到地址的人只能到达一样东西：节点在隧道里的 libp2p 监听，和它的 TCP、QUIC 端口提供的是同一个；隧道不通向别的服务，也不通向这台机器所在的网络。
- **DERP 看到的和中继一样**：两端的地址、交换了多少、什么时候；看不到内容。默认的 DERP 是 tailcat 的公共 DERP，由 Tailscale 运营，不属于本网络：介意的部署把 `tailnet.derp_map` 指向自己的 DERP。
- **卖家不能决定买家连到哪里。** 买家在自己的表里查地址的 DERP 区域，表里没有就拒绝。
- **直连的两端互相看得到对方的 IP 地址**，和打洞成功之后一样。只想让中继看到自己地址的用户不要打开 tailnet（并把 `nat` 设为 false）。

## 3. 账户、设备和平台

| 威胁 | 防御 | 代码 |
|---|---|---|
| 把别人的设备绑到自己的账户上，截走它的收入 | 绑定需要设备对用户名、peer ID 和时间戳的签名，时间戳要在五分钟以内。已绑定的设备不能再绑到别处。 | `internal/accounts` |
| API token 被盗 | token 可以随时吊销，登录 token 会过期，数据库里只存 SHA-256。 | `internal/accounts`、`internal/portal` |
| 猜登录验证码 | 没有密码：登录需要发到账户邮箱的 6 位验证码。验证码 10 分钟有效，可以试 5 次；一个邮箱每小时最多 5 个验证码（每个 IP 20 个，全站 500 个）；错误的验证码还按 IP 和邮箱限流。只保存验证码的加盐哈希，邮件发出后从发件箱清除。 | `internal/mailer/codes.go`、`internal/portal/auth.go` |
| 别人能读你的邮箱 | 邮箱就是账户的钥匙：能读它的人就能登录。用户可以在账户页加开 TOTP 两步验证，开启和关闭时都会发邮件通知。没有可用发件人的门户谁都登录不了。 | `internal/portal/mfa.go` |
| 被禁用的用户继续交易 | 协调器每次请求都检查用户状态，token 立即失效，中继凭证在有效期内（默认一小时）用完。 | `internal/accounts`、`internal/relaypass` |
| 管理员邮箱被别人读到 | 管理员强制 TOTP 两步验证，不能关闭。没有经过两步验证的 token 进不了管理 API。错码有限流，一个 challenge 错五次作废，同一个验证码不能重放。TOTP 密钥加密存放（AES-GCM）。 | `internal/portal/mfa.go`、`internal/totp` |
| 网页会话被窃取、跨站请求伪造、脚本注入 | 会话放在 HttpOnly、SameSite=Strict 的 cookie 里，而且只有同时带自定义请求头才有效，Origin 必须是门户自己。严格的 Content-Security-Policy 不允许内联代码和第三方资源。页面用文本构建 DOM，从不拼接 HTML 字符串。 | `internal/portal/web.go` |
| 窃听与门户之间的连接 | 默认 HTTPS。自签名证书由客户端按指纹固定，客户端拒绝把登录验证码以明文 HTTP 发往其他机器。 | `internal/portal/tls.go`、`internal/client` |
| 网页调用本机客户端 API 来花用户的 credit | 本机 API 只绑定回环地址，拒绝 Origin 不是本机的请求。 | `internal/client` |
| 绕过中继直连协调器 | 协调器不监听任何地址。 | `cmd/coordinator` |
| 陌生人占满中继的预约名额 | 预约需要门户签发、绑定到设备 peer ID 的短期凭证，每个用户的设备数有上限。中继离线验证凭证。 | `internal/relaypass`、`internal/relay` |
| 用超大帧或海量流耗尽内存 | 帧按实际到达的数据增长，不按声明的长度预分配。流处理器先向 libp2p 的资源管理器预留内存，每条流、每个 peer 和全局都有上限。 | `internal/protocol`、`internal/p2p` |
| 中继宕机 | 客户端自动切换中继。卖家在不止一个中继上预约，协调器在所有中继上预约。 | `internal/client`、`internal/p2p` |
| 篡改账本 | 复式记账：每笔变动都是平衡的转账，写入日志，启动时回放日志与余额对账。门户和协调器的所有写入由同一把数据库锁串行化。 | `internal/ledger`、`internal/mysqldb` |
| 陌生人发来的邮件 | 邮件服务只收列出的邮箱，不转发，控制台里只显示纯文本，附件只能下载。它不需要访问账本和用户表。 | `internal/mailer` |

用户机器上保存机密的文件（设备密钥、带登录 token 的配置、厂商凭据）创建时就只有本用户可读：Unix 上是 0600 权限，Windows 上是 ACL（`internal/secfile`）。

## 4. 边界

这一节直接说明限制。决定是否依赖这个网络的人，比起上面的清单更需要知道这些。

- **没有 TEE 时卖家能读到 prompt。** 模型不能在密文上运行。加密把信任边界移到了卖家的机器上，只有硬件证明才能把运营者排除在外。需要这一点的买家要设置 `require_tee`。
- **出售托管 API 的卖家会把 prompt 转交出去。** 转售托管 API 的卖家用自己的账号把请求发给那家服务商。买家的数据因此还要受那家服务商的政策约束，卖家自己负责遵守那家服务商的服务条款。
- **抽检是概率性的，而且需要参考模型。** 如果卖家能分辨抽检和真实作业，就可以只在被抽检时守规矩。转交的题目来自真实买家的设备，走的是那个买家平时的路径（直连或经中继），但它仍然是一段很短的、贪心解码的对话，卖家可以对所有这类请求守规矩、只在长请求上作弊。转交的客户端知道这个卖家此刻被抽检了（不知道题目，也不知道结论）；同时运行买家客户端的卖家可以利用这一点。客户端也可以拒绝转交或弄丢转交的内容，这会让平台白付一单，但不会影响卖家的记录。卖家会看到转交设备的 peer ID 和地址，和这台设备自己买的任何作业一样。没有客户端可以转交的题目来自一个新身份、经官方中继，卖家能把它和常来的买家区分开。逐 token 核对证明的是回答的行为像参考模型，不是密码学证明。只有参考方给 logprobs 的模型才能核对：自建服务上的开源权重模型、DeepSeek、OpenAI 的非推理模型。其他模型没有任何手段能证明文本是哪个模型生成的。
- **没有参考模型时，用量检查比较宽松。** 备用的 token 计数是估算，只能抓住严重的多计。
- **硬件证明只和镜像一样可靠。** 白名单里的度量值必须对应一个可复现的构建，它把密钥留在内存里，并且只提供固定的模型。CPU TEE 不保护 GPU 显存。侧信道和厂商固件漏洞不在范围之内。
- **卖家自己的中继能看到买家的地址。** 买家经卖家的私有中继连到节点时，这个中继看到买家的网络地址、时间和流量：这些本来就是直连时卖家能看到的，现在在买家无法直连时也能看到。它看不到内容。
- **经中继的连接没有准入控制。** 任何人都可以向已预约的 peer 发起 circuit。对方会认证并拒绝陌生人，但中继的带宽已经被占用，只有总量上的限制。
- **配对是撮合规则，不是加密。** 它决定买家的请求发给哪些卖家。配对的卖家能看到 prompt 的哪些内容并没有变化；保存配对的是平台，平台可以改动它。
- **共享伙伴同样是撮合和计费规则。** 伙伴关系和共享标记由平台保存，平台可以改动它们，或者对标为免费的任务收费。
- **中继能看到元数据。** 它看得到谁连接谁、什么时候、多少流量，看不到内容。
- **平台在记账上是受信任的。** 账本由一个协调器和一个门户持有。它们读不到 prompt，但不诚实的运营方可以错报余额。credit 由管理员发放，没有链上或外部结算。
- **自签名的门户证书依赖第一次核对。** 用户必须把指纹和运营方公布的对一遍。有域名时，公共 CA 签发的证书更好。

## 5. 给运营方的建议

- 每个服务端程序用单独的系统用户运行，密钥文件只有该用户可读。门户的凭证签名密钥、协调器的密钥和邮件服务的 DKIM 密钥没有理由互相可读。
- 给邮件服务一个只能访问它自己那几张表的数据库账号。
- 数据库只允许门户和协调器所在的机器连接。
- 备份门户的凭证签名密钥、自签名证书目录（如果在用）、协调器的密钥、每个中继的密钥和数据库。丢失密钥会改变一个已经被别人固定的身份。
- 配置文件里不放机密：只写环境变量名或文件路径（[configuration.md](configuration.md)）。
- 中继的状态和指标端点没有认证，只能绑定回环地址。通过 SSH 或带认证的代理读取。
- 协调器配置里的 `dev.open_accounts` 只用于测试网络：它允许未注册的 peer 交易。
