# sharetoken 设计文档：可验证、保密的开源模型 token 共享网络

> 版本 v1（2026-11-07）。本版的多机实测与压测结果见 [validation-v1.md](validation-v1.md)。

sharetoken 是用 Go 实现的 P2P 推理网络：大家把自己机器上跑的**开源权重模型**的闲置算力共享出来，赚到 credit，需要时再用 credit 调用别人的节点。

**定位**：只做开源模型的 token 共享，不转发 OpenAI、Anthropic 等闭源服务（订阅和 API key 都不转发），因此也不设模型白名单。开源权重让「验证节点到底跑了什么」第一次变得可行，后面几节的机制都建立在这个前提上。

设计重点是买家侧的两个空白：

1. **响应完整性**：买家拿到的每一字节就是节点签字认账的那一份，没被篡改、截断、重排、调包；用量没被虚报；节点跑的确实是它声称的模型。
2. **Prompt 保密**：prompt 不经过协调器，中继和网络读不到；在 TEE 部署下，节点运营者也读不到。

## 1. 密码学能做到什么、做不到什么

纯密码学能完全保证：传输链路不被读、不被改；节点对自己交付的内容不可抵赖；Ticket、Offer、Ack 不可伪造、不可重放；计费不超过预留金额。

纯密码学单独保证不了：节点签字的内容是不是「真模型跑出来的」。对闭源模型这一点根本无解（权重保密、厂商不签名）；对**开源模型**则有三条路，本项目全部实现：

| 机制 | 回答的问题 | 性质 |
|---|---|---|
| 证据裁决（`evidence`） | 这一单是否交付了不可读内容、是否虚报用量 | 确定性，可证明 |
| 抽检（`audit`） | 节点平时跑的是不是它声称的模型 | 概率性，可惩罚 |
| TEE 远程证明（`attest`） | 节点上跑的是不是审计过的镜像；运营者能否看到 prompt | 硬件信任根 |

## 2. 架构

```
                 ┌──────────────────────────────────────────────────────┐
                 │ Coordinator（控制面，不在数据通路上）                     │
                 │  GossipSub 订单簿 · 撮合 · 签发 Ticket · 结算            │
                 │  SQLite：账本 / 作业 / 节点档案 / 抽检记录                │
                 │  证据裁决 · 抽检执行器 ──► 参考模型（同一开源权重）         │
                 └────▲───────────────▲───────────────────▲───────────────┘
      签名 Offer(+quote)│      Ticket 请求│   结算(收据+Ack) / 证据 │
                      │               │                   │
   ┌──────────────────┴───┐  直连流   ┌─┴───────────────────┴──┐
   │ Node                  │◄════════►│ Buyer                   │
   │ libp2p 身份 = 签名身份  │  Noise   │ 每单一把 X25519 密钥      │
   │ X25519 收件钥（box）    │  E2E     │ 本地代理 127.0.0.1:9787  │
   │ 可选：CVM 内生成密钥+quote│          │ 校验收据→Ack，或带证据争议 │
   └──────────┬────────────┘          └─────────────────────────┘
              ▼
       Ollama / vLLM / llama.cpp / SGLang（开源模型）
```

- **数据面**：买家和节点直连（`/sharetoken/infer/1.0.0`），NAT 后的节点经协调器的 circuit relay v2 中转，中继只看到 Noise 密文。
- **控制面**：`/sharetoken/ctrl/1.0.0`。
- **唯一的例外**：买家**主动**提交证据时，协调器能读到**那一单**的内容（见第 5 节）。

## 3. 一次请求的完整链路

```
Node                         Coordinator                          Buyer
 │ ① 签名 Offer{Addrs,BoxPub,ReceiptKey,价格,有效期,[TEE quote]}        │
 │──── GossipSub ────────────────►│ 验签 + 发布者==Node；有 quote 则验证   │
 │                                │◄──── ② TicketRequest{模型,预算,      │
 │                                │        [require_tee],[指定节点]} ────│
 │                                │ 撮合（排除被暂停节点）→ 冻结预算 → 签 Ticket
 │                                │───── Ticket + 节点亲签 Offer ────────►│
 │                                │  ③ 买家核对：协调器签名；Ticket 与 Offer 的
 │                                │     密钥/地址/价格一致；require_tee 时自己验 quote
 │◄═══ ④ InferRequest{Ticket, JobPub, SealFrom(jobKey→NodeBoxPub, prompt)} ══│
 │ ⑤ checkTicket；并要求 JobPub == Sealed[:32]（请求的发送方密钥就是响应的收件钥）
 │ ⑥ 逐块 Seal(块→JobPub, AAD=job|model|seq)，对密文做流式哈希 ═══════════►│ 逐块解密
 │ ⑦ 签收据{reqHash, respHash, model, usage, nonce} ═════════════════════►│ BuyerCheck
 │◄════════════════════════════════════ Ack，或 Reject + 争议（可带证据）══│ + 用量检查
 │ ⑧ Settle{Ticket, Receipt, Ack} ─►│ 按 Ticket 价格计费（≤ 预留），在一个 SQLite 事务里
 │                                │ 完成分账和作业状态变更
```

## 4. 威胁 → 防御 → 代码

| 威胁 | 防御 | 代码 |
|---|---|---|
| 协调器读取 prompt | 协调器不在数据面；请求另用 box 封装到节点密钥 | `node`、`box` |
| 中继或网络读取、篡改 | Noise 端到端 + box 双层加密 | `p2p`、`box` |
| 协调器替换节点的 BoxPub（中间人） | 买家逐项核对 Ticket 与**节点亲签的 Offer** | `buyer.verifyTicket` |
| 节点签字后交付的内容与签字时不同 | respHash 不一致，`BuyerCheck` 拒绝 | `receipt.BuyerCheck` |
| 分块被丢弃、重排、拼接 | 每块 AAD 含序号；哈希带长度前缀 | `protocol.ChunkAAD` |
| **虚报用量** | 买家先做合理性检查；拒签后提交证据，协调器用参考模型的 tokenizer 精确计数后裁决 | `evidence`、`tokens` |
| **交付不可读的内容（垃圾密文）** | 证据中某块用本单密钥解不开 → 判节点败诉 | `evidence.Judge.Add` |
| **一单签两张收据** | 结算的收据与买家出示的不同 → 判节点败诉 | `evidence.New`、`ApplyVerdict` |
| 买家伪造证据 | 请求和分块必须与节点签名的哈希一致，否则只能判「无法验证」 | `evidence` |
| 买家披露错误的密钥来诬陷节点 | 请求密文以发送方公钥开头，签名哈希锁定了它；不匹配就判买家败诉 | `evidence.New` |
| **用小模型/别的模型冒充** | 随机抽检：同样请求在参考模型上重算，相似度低或用量超标即判不符；连续两次暂停接单 | `audit`、`coordinator.RecordAudit` |
| **节点运营者读取 prompt** | TEE：密钥在机密虚拟机内生成，quote 同时绑定收件钥和签名钥 | `attest`、`attest/sevsnp`、`attest/tdx` |
| 拿别的节点的 quote 冒充 TEE | quote 的 report data 绑定本 Offer 的两把公钥 | `attest.Policy.Check` |
| 调试模式/可迁移的 CVM | 策略拒绝 debug；SEV-SNP 拒绝允许迁移代理的 policy | `attest`、`attest/sevsnp` |
| 协调器重启丢账、重复付款 | 全部状态在 SQLite，每次状态变更是一个事务 | `ledger`、`coordinator/store.go` |
| 绕过账本直接改库 | 启动时回放日志对账，余额对不上就拒绝启动 | `ledger.Reconcile` |
| 用另一个协调器的密钥打开数据库 | 库里记录协调器身份，不匹配拒绝 | `coordinator.NewEngine` |
| Ticket 重放 / 盗用 / 伪造 | 一次性集合；绑定买家 peer ID；协调器签名 + 原件比对 | `node.markSeen`、`checkTicket`、`Ticket.Equal` |
| 买家放大工作量（`n`、`best_of`） | 节点按字段白名单转发 | `node.prepareUpstreamBody` |
| 超额消费 | 预留冻结；`MaxOutputTokens`；结算 ≤ 预留 | `protocol/cost.go` |
| 跨类型重放签名 | 域分隔的规范编码 | `internal/canon` |

## 5. 基于证据的争议（`evidence`）

**关键设计：一把密钥，打开且只打开一单。**

1. 买家为每一单生成新的 X25519 密钥 `jobKey`，用它作为**发送方**封装请求（`box.SealFrom`），密文的前 32 字节就是 `jobPub`。
2. 节点要求 `BuyerBoxPub == Sealed[:32]`，并把每个响应块封装**给** `jobPub`。
3. 收据签的是 `SHA-256(Sealed)`，所以节点的签名同时锁定了响应收件钥。

发生争议时，买家提交 `jobKey` 私钥、请求密文和全部响应密文块。协调器边接收边判断：

| 检查 | 不通过时 |
|---|---|
| 请求密文的哈希 == 收据里的 reqHash | 无法验证（转人工） |
| 响应块的流式哈希 == 收据里的 respHash | 无法验证（转人工） |
| 披露的密钥 == 请求密文开头的公钥，且能解开请求 | 买家败诉（付款给节点） |
| 每个响应块都能用 jobKey 解开 | **节点败诉**（退款 + 信誉 −50） |
| 用量 ≤ 实数 token 的容许上限 | **节点败诉** |
| 结算收据与买家出示的收据相同 | **节点败诉**（一单两签） |

- **精确计数**：协调器配置了某个模型的参考服务器时（`-reference`），prompt 直接按原请求取 `usage.prompt_tokens`（同一 tokenizer 和对话模板）；生成文本用差分法：`prompt_tokens(文本) − prompt_tokens(空)`，模板开销互相抵消。容许上限是实数 +5% +16。已在 Ollama 0.40 上实测：提示缓存命中时 `prompt_tokens` 仍报全量。没有参考模型时用启发式，上限放宽为 3×+512 / 2×+64，只抓明显虚报。
- **隐私**：只有买家**自己的检查已经失败**时才会提交证据，且只暴露那一单。协调器只在内存里解密和计数，日志只记结果。买家可用 `-evidence=false` 关闭，此时争议转人工。
- **证据证明不了的**：节点没签过的东西（「它发给我的不是这个」），判为「无法验证」，留给人工仲裁（`coordinator resolve <job> pay|refund`）。

## 6. 抽检执行器（`audit`）

协调器运营者为某个模型配置参考副本（`-reference id=…,upstream=…,url=…`）后，抽检器按指数分布的随机间隔运行：

1. 生成**全新身份**，从平台手续费账户拨款（账户可以为负，表示运营者补贴），作为普通买家向目标节点购买一次补全。节点看到的是一个新买家，所有收据校验照常进行。
2. 挑战 prompt 是随机生成的短问题（乘法、列素数、倒拼单词等），答案受约束，用 temperature 0 加固定 seed，节点无法缓存答案。
3. 用 `node.UpstreamRequest` 构造**与诚实节点逐字节相同**的上游请求，发给参考模型。
4. 比较：按词、数字、标点、中日韩单字做 LCS 相似度；同时用参考模型自报的用量检查收据。
   - 相似度 ≥ 0.8 且用量正常 → 通过（信誉 +5）。
   - 相似度 < 0.4，或用量超标，或收据被拒 → 不符（信誉 −100）。**连续两次不符暂停接单 24 小时**。
   - 介于两者之间 → 不确定，不奖不罚，避免硬件数值差异冤枉诚实节点。
5. 结算后，审计身份的剩余 credit 由 `Tick` 退回平台账户。

经济含义（Proof-of-Sampling）：抽检率 p、罚额 S 时，作弊比例为 c 的节点每单期望损失 p·c·S，S 足够大时诚实是占优策略。

**局限**：审计连接来自协调器的网络位置（与经中继到达的普通买家相同）；需要更强掩护时，应把抽检器放到独立出口。只有配置了参考模型的模型才能抽检。

## 7. 真实 TEE（`attest`）

**绑定**：节点在机密虚拟机（AMD SEV-SNP 或 Intel TDX）里启动时，在内存中生成全部密钥（不写盘，因此 peer ID 每次启动都会变），然后请求硬件签一份 quote，其中 report data 为

```
ReportData = SHA-512(canon("sharetoken/attest/v1", ReceiptKey, BoxPub))
```

**两把公钥都绑定**：如果只绑定签名钥，宿主机可以把收件钥放在虚拟机外面偷看 prompt，同时让虚拟机内的代码签收据。

**验证**（买家必做，协调器可选，用于 `require_tee` 撮合）：

| 后端 | 验证内容 | 度量值 |
|---|---|---|
| AMD SEV-SNP | VCEK → ASK → ARK 证书链到 AMD 根（库内置）；报告 ECDSA P-384 签名；拒绝允许迁移代理的 policy；报告 debug 位 | 报告里的 `MEASUREMENT`（48 字节） |
| Intel TDX | quote v4 的 QE 签名、PCK 证书链到 Intel SGX 根（库内置）；可选在线拉取 TCB 状态 | `SHA-384(MRTD‖RTMR0‖RTMR1‖RTMR2)`（RTMR3 运行时可扩展，排除） |

然后用策略文件（`-tee-policy`）检查：report data 等于本 Offer 两把公钥的绑定值、不是 debug guest、度量值在白名单里。默认离线验证签名链；`-tee-online` 额外检查吊销和 TCB 状态。

**测试**：SEV-SNP 用 go-sev-guest 的测试用 AMD 密钥体系生成真实签名的报告，覆盖篡改、debug、迁移代理、非 AMD 根；TDX 用 Intel 的**真实生产 quote 样本**验证到 Intel 根，并覆盖篡改和证书过期。真正在 CVM 内取 quote（`attest/hw`）需要 Linux 机密虚拟机实机，这台 Mac 上无法运行。

**局限**：可信度取决于镜像本身。白名单里的度量值必须来自可复现构建、只在内存里持有密钥、并固定所服务模型的镜像。CPU TEE 不覆盖 GPU 显存，GPU 推理还需要 GPU 的机密计算模式（NVIDIA H100 及以后）和它自己的证明，目前尚未接入。侧信道和厂商固件漏洞不在范围内。

## 8. 结算状态机与互助账本

```
held ──有效 Ack──────────────────────────────────────► final
held ──无 Ack──► pending ──争议窗口（24h）到期────────► final
                 pending ──普通争议──► disputed ──人工仲裁──► final | refunded
held | pending | disputed ──证据裁决──► final（买家败诉）| refunded（节点败诉）| disputed（无法验证）
held ──截止前无人结算──────────────────────────────────► released（全额退回）
```

- **SQLite 持久化**：账本、作业、节点档案、抽检记录、开发 credit 发放记录都在同一个数据库里。每个状态变更是一个 `BEGIN IMMEDIATE` 事务（WAL，`synchronous=FULL`），钱和作业状态同进同退。Offer 不持久化，节点每 15 秒重新广播一次。
- **对账**：启动时从日志回放每个账户的余额，检查总和为 0、每个冻结账户正好等于未结冻结额，任何一项对不上就拒绝启动。`coordinator check` 可随时执行。
- **运维命令**直接操作数据库，可与运行中的协调器并存（SQLite 负责跨进程串行化）：`deposit`、`balance`、`disputes`、`resolve`、`nodes`、`audits`、`check`。
- **一个 peer 一个账户**：卖出赚到的 credit 可以直接用来买（`TestMutualAidEarnThenSpend`）。credit 是封闭体系内的记账单位，不接现金。
- **信誉**（0–1000，初始 500）：成功 +1，超时 −5，争议败诉 −50，抽检通过 +5，抽检不符 −100，连续两次不符暂停接单。

## 9. 诚实的边界

- **没有 TEE 时，节点运营者能看到明文 prompt。** 只有在节点运行于证明通过的镜像中、买家要求 `require_tee` 时，运营者才被移出信任基。
- **GPU 推理的 TEE 还不完整**：需要 GPU 机密计算模式的证明，尚未接入。
- **抽检是概率性的**：会区分审计和真实流量的节点可以只在被审计时守规矩；随机 prompt 和全新身份能提高区分难度，但做不到不可区分。
- **证据裁决依赖参考模型**：没有参考模型时只能用宽松的启发式上限。
- **无法证明「没收到」**：节点没签过的内容，证据无能为力，只能转人工仲裁。
- **女巫攻击**：自我交易只拦了同一 ID；`-dev-credit` 只能用于开发环境。需要质押才能根本解决。
- **协调器仍是账本的可信方**：它伪造不了收据、Ack 和证据结论的依据，但账本由它记录。
- **没交付就失败的单会占着节点的并发名额**：买家连不上节点时，这一单保持 `held` 直到截止（约 17 分钟），一直计入节点的在途单数，到期还扣节点 5 点信誉。恶意买家只申请 Ticket 不去连，就能几乎零成本地把节点挡在市场外。
- **协调器吞吐有限**：全局一把锁、单写者、每次提交都刷盘，云盘上约 150 单/秒；撮合时逐个节点查信誉，5,000 个节点时降到约 16 单/秒（见 validation-v1.md）。
- **中继容量用的是 go-libp2p 默认值**：整个协调器最多 128 个中继预约、同一公网 IP 最多 8 个、每个节点最多 16 条中继连接。运营商级 NAT 下，多个用户共用一个公网 IP，很容易撞上第二条。

## 10. 下一步

v1 实测发现、应当优先处理的：

1. **释放失败单的并发名额**：买家提交「没交付」的争议时立即释放名额，不扣节点信誉。
2. **撮合改为内存索引**：节点信誉和在途单数在内存里维护，按模型索引，消除撮合时逐个节点查库。
3. **写入合并提交**、只读操作不拿写锁。
4. **中继容量配置化**：放开或可配置预约数和单 IP 上限；验证打洞（DCUtR）在真实网络里是否生效。
5. **正式的压测工具**：覆盖网络层、长时间运行、大账本启动时间。

1. **质押与罚没**：把信誉惩罚变成经济惩罚，抵御女巫攻击。
