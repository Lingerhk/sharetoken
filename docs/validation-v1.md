# sharetoken v1 验证报告：跨公网多机实测与协调器压测

> 版本 v1（2026-11-07）。设计说明见 [design-v1.md](design-v1.md)。

## 1. 测试环境

| 机器 | 硬件 / 系统 | 网络位置 | 角色 |
|---|---|---|---|
| 云服务器 | x86_64，2 核 2 GB，CentOS 7 | 公网 IP，云安全组只开放部分端口（用了 TCP 8091） | 协调器（同时做中继）+ 买家 |
| Mac | Apple Silicon，Ollama 0.40，gemma4:e4b | 家庭宽带 NAT 后 | 诚实卖家 |
| armbian | aarch64，2 GB | 同一家庭局域网 | 作弊卖家：报价更低，把补全 token 数虚报 100 倍（`scripts/inflating_upstream.py`） |

- 全程只有一份真实模型：协调器的参考模型、作弊节点的上游，都通过 SSH 反向隧道接到 Mac 的 Ollama。
- 云服务器上传带宽很低，传二进制会卡住。改为在服务器上用 Go 1.26 从源码编译，只传源码包（约 130 KB）。

## 2. 结果

| 验证项 | 结果 |
|---|---|
| 公网买家经中继连到 NAT 后的节点 | ✅ 买家与两个卖家之间没有直连 TCP，推理流量全部经协调器中继（Noise 密文） |
| 响应校验 | ✅ 每个回答都带 `X-Sharetoken-Verified: true`，耗时 2.5–15 秒 |

| 非流式请求自动换节点 | ✅ 作弊被抓后改走诚实节点，调用方无感 |
| 流式请求 | ⚠️ 符合设计：内容已发出，无法换节点，末尾补 `receipt_rejected` 错误事件，钱照样退回 |

## 3. 发现的问题

### 3.1 抽检器无法拨通 NAT 后的节点（v1 已修复）

抽检器用仅拨出的临时主机（`p2p.HostConfig{DialOnly: true}`），实现里用了 `libp2p.NoListenAddrs`。在 go-libp2p v0.51 中这个选项会同时关闭中继传输，于是拨 `/p2p-circuit` 地址时报 `no transport for protocol`。本地测试里节点都有直连地址，所以没暴露；但家用节点正是主要场景，等于抽检完全失效。

- 修复：`p2p/host.go` 在 `NoListenAddrs` 之后加 `libp2p.EnableRelay()`。
- 回归测试：`p2p/host_test.go` 的 `TestDialOnlyHostDialsRelayedNode`。去掉修复会失败，加上修复通过。

### 3.2 没交付就失败的单占着节点的并发名额（未修复）

买家连不上节点时，这一单保持 `held` 直到截止（约 17 分钟）。买家虽然提交了「没交付」的争议，但状态不变，继续计入节点的在途单数（`busyNodes` 只统计 `held`）。

- 实测影响：诚实节点被两个这样的单占满（默认并发 2），看起来像不在线，抽检器也找不到它。到期时节点每单还被扣 5 点信誉。
- 风险：恶意买家只申请 Ticket 不去连，就能几乎零成本地把节点挡在市场外。
- 建议：协调器收到「没交付」的争议时立即释放名额，并且不扣节点信誉。

### 3.3 部署注意事项

- **公网协调器不要加 `-nat=false`**：这会关掉 AutoNAT 服务，节点判断不出自己在 NAT 后面，拿不到中继地址，买家拨号失败。
- **虚拟组网会绕开中继**：测试机器之间还有一层 ZeroTier 虚拟网。节点监听 `0.0.0.0` 时会通告虚拟网地址，买家直接连过去，中继路径根本没走到。要测 NAT 场景，节点应只绑定局域网地址。

## 4. 协调器压测

### 方法

临时测试直接调用 `coordinator.Engine`：签发 Ticket → 节点签收据 → 带 Ack 结算，算作一单。数据库是真实 SQLite 文件（WAL，`synchronous=FULL`），每个场景跑 4 秒。不含网络层。

### 结果

| 场景 | Mac：单数/秒 | 云服务器：单数/秒 | 云服务器：签发 Ticket 的 p50 / p99 |
|---|---|---|---|
| 10 个节点，1 个并发 | 1,582 | **148** | 3 ms / 6 ms |
| 10 个节点，64 个并发 | 1,396 | **150** | 224 ms / 277 ms |
| 1,000 个节点，64 个并发 | 138 | **48** | 796 ms / 1.4 s |
| 5,000 个节点，64 个并发 | 32 | **16** | 3.3 s / 6.3 s |

macOS 的 `fsync` 不保证真正落盘，Mac 的数字偏乐观；云服务器更接近生产。

### 瓶颈分析

1. **撮合的开销随节点数线性增长**（最严重）。`IssueTicket` 在全局锁内遍历所有挂单，对每个价格合格的节点单独查一次库读信誉（`loadStats`），还要整表统计在途单数（`busyNodes`）。
2. **全局串行 + 每次提交都刷盘**：`Engine.mu`、单个数据库连接、`synchronous=FULL`。每单至少两次写事务，云盘上上限约 150 单/秒；加并发不提高吞吐，只增加排队延迟。查余额、列模型这类只读操作也要拿同一把锁。
3. **中继容量**（读 go-libp2p v0.51 默认值得出，未实测）：最多 128 个中继预约，同一公网 IP 最多 8 个，每个节点最多 16 条中继连接。经中继的推理流量全部走协调器带宽；本次实测里打洞没有生效过。
4. **节点侧**：默认并发 2，上限取决于模型服务本身；再叠加 3.2 的名额占用问题。
5. **其他**：每次抽检都新建一个 libp2p 主机；`Tick` 处理到期单时每单开一个事务；启动时回放整个账本日志对账，没有快照。

### 尚未覆盖

网络层（中继吞吐、大量并发连接、打洞成功率）、长时间稳定性、大账本下的启动时间、上千节点时的挂单广播开销、真实多机环境下的端到端压测。
