# Translations

The landing page, the user portal (`/app/`) and the desktop client are available in 20 languages. The admin console stays in Chinese: `admin.html` pins `data-lang="zh-CN"`, so the same `common.js` runs there without a dictionary.

Chinese is the source language and the source text is the key: `tr('登录')`. Dictionaries are flat JSON, `{ "<Chinese source>": "<translation>" }`, one per bundle and language:

| Bundle | Page | Dictionaries |
| --- | --- | --- |
| `site` | landing page | `portal/web/i18n/site/<lang>.json` |
| `app` | user portal, shared login | `portal/web/i18n/app/<lang>.json` |
| `client` | desktop client | `client/ui/i18n/client/<lang>.json` |

The language comes from `?lang=`, then the saved choice (`localStorage.st_lang`), and otherwise English: the browser's or system's language does not choose it. `portal/web/i18n.js` and `client/ui/i18n.js` are identical copies of the runtime.

## Changing text

1. Put new text through `tr('…')` in one literal (`parts('…{x}…', {x: node})` when it contains an element). Write whole sentences with `{placeholders}`, never concatenate pieces. Static HTML needs nothing, its exact text is the key; an element with inline markup gets `data-i18n-rich`, and only `<br>`, `<em>`, `<strong>` may appear in it.
2. Avoid sentences that depend on a count's plural form. There is no plural engine. Write translations as a label and a number, like `Jobs: {n}`.
3. Run `go test ./portal -run I18n`. It lists every missing or stale key, broken placeholder and Chinese text that bypasses `tr()`. `I18N_DUMP=<dir>` writes each bundle's source strings to that directory.

## Translation rules

The Chinese text is authoritative; the English dictionary shows the intended tone.

- Keep unchanged: `{placeholders}`, `<br>`, `<em>`, `<strong>`, `|` separators, `→`, `·`, numbers, command lines, and these names: ShareToken, sharetoken, OpenAI, Ollama, TEE, CSP, SHA-256, X25519, Ed25519, HKDF, AES-GCM, Noise, libp2p, Argon2id, TOTP, RTT, API, CLI, HTTP, URL, JSON headers and field names, `respHash`, `peer`/`peer ID`, Ack, Offer, Ticket, `prompt`, `token`/`tokens`, `credit`.
- Use one established rendering consistently for: relay (中继), coordinator (协调器), portal (门户), node (节点), buyer (买家), seller (卖家), job (作业), receipt (收据), dispute (争议), device (设备), ledger/bill (账单), two-factor authentication (两步验证).
- Security statements stay exactly as strong as the source, never stronger. Ordinary nodes *can* read prompts, the coordinator *is* the trusted ledger, audits *are* probabilistic. Do not soften or embellish them.
- Short labels stay short: buttons, table headers, badges and navigation sit in tight layouts.
- Use a neutral, direct, informal-but-polite register for addressing the user, as a well-translated developer tool would.
